## User Scenarios & Testing *(mandatory)*

### User Story 1 - Populate purchase attachment records from the ERP's Sales Order Template data (Priority: P1)

A Data Administrator needs the compliance system's Sales Order ↔ Purchase Order ↔ Template mapping records to reflect what is recorded in the company's ERP system. Today, this mapping (used elsewhere to show which template applies to a sales order) has to be created by hand. The administrator wants to trigger a synchronization action that pulls the full set of Sales Order Template records from the ERP reference data and creates the corresponding local mapping records automatically, without creating duplicate entries for sales orders that already have a mapping.

**Why this priority**: This is the entire scope of the requested change — a one-shot data sync action. Without it, the feature delivers no value.

**Independent Test**: Trigger the synchronization action against an ERP reference dataset that contains a mix of sales orders with no existing local mapping and sales orders that already have one. Confirm that after the run, every previously-unmapped sales order now has exactly one mapping record with the correct Purchase Order and Template values, and that sales orders which already had a mapping are left unchanged (no new or duplicate record created for them).

**Acceptance Scenarios**:

1. **Given** the ERP reference data contains a Sales Order Template record for a sales order that has no existing mapping record, **When** the synchronization action runs, **Then** a new mapping record is created with Sales Order ID, Purchase Order ID, and Template Code taken from that reference record.
2. **Given** the ERP reference data contains a Sales Order Template record for a sales order that already has a mapping record, **When** the synchronization action runs, **Then** no new record is created and the existing mapping record is left unchanged.
3. **Given** the ERP reference data spans more records than fit in a single page/batch of the underlying reference lookup, **When** the synchronization action runs, **Then** every record across all pages is evaluated (not just the first page).
4. **Given** the synchronization action has already been run once with no changes to the ERP reference data since, **When** it is run again, **Then** no additional mapping records are created (the second run is a no-op).

### User Story 2 - Detect and alert on purchase orders with incomplete EUTR documentation (Priority: P1)

A Compliance Admin needs to know, across the entire population of ERP purchase orders, which ones are not yet fully covered by EUTR compliance documentation — either because no compliance template was ever assigned to them, no document folder has been created for them yet, or some of their assigned template's required document steps still have no uploaded document. Today this can only be discovered by inspecting purchase orders one at a time. The admin wants to trigger a single check that scans the entire ERP purchase-order population, works out exactly what (if anything) is missing for each one, and emails the team(s) responsible for each affected purchase order's template an Excel report listing only the purchase orders that have a problem, with enough detail to act on it.

**Why this priority**: This is the primary new capability requested in this update — without it, incomplete purchase-order documentation is only ever found reactively, one purchase order at a time.

**Independent Test**: Trigger the check against an ERP purchase-order dataset containing a mix of purchase orders with no template assigned, purchase orders with a template but no document folder, purchase orders with a folder but missing document(s) for one or more of their template's steps, and purchase orders that are fully complete. Confirm that after the run, exactly one email per distinct responsible Alert group is sent, each with an Excel attachment listing only the affected purchase orders relevant to that group, each row carrying the correct reason(s) it was flagged, and that fully-complete purchase orders appear in no email and no attachment.

**Acceptance Scenarios**:

1. **Given** the ERP purchase-order reference data spans more records than fit in a single page/batch of the underlying reference lookup (over 3,000 records), **When** the check runs, **Then** every purchase order across all pages is evaluated exactly once before the run finishes.
2. **Given** a purchase order has no compliance template value recorded in the ERP data, **When** it is evaluated, **Then** it is flagged with the note "Missing template id", and no folder or step check is performed for it.
3. **Given** a purchase order has a compliance template value recorded, but no document folder named exactly after that purchase order's ID exists at the system's configured EUTR document location, **When** it is evaluated, **Then** it is flagged with the note "No PO folder", and no step-level check is performed for it.
4. **Given** a purchase order has a compliance template value recorded and its document folder exists, **When** it is evaluated against every document step configured on that template, **Then** each step for which no document has been recorded against that purchase order is listed in its note as one line per missing step, in the form "{n} - {step name} - Missing", where step name comes from Step Management (001-eutr-steps) and `n` is sequential among that purchase order's own missing steps (updated 2026-08-14 — previously showed the template's own name plus the step's absolute position instead of the step's name).
5. **Given** a purchase order has a compliance template value recorded, its document folder exists, and every step of its template already has at least one recorded document, **When** it is evaluated, **Then** it is not flagged (no note) and it does not appear in the report or any email.
6. **Given** the check has finished evaluating every purchase order, **When** the report is assembled, **Then** the Excel attachment(s) and email content include only flagged purchase orders (a non-empty note) — unflagged purchase orders are excluded entirely.
7. **Given** the flagged purchase orders in a run resolve to more than one distinct responsible Alert group (via their templates' configured Alert group), **When** notifications are sent, **Then** one separate email is sent per distinct Alert group, each with its own Excel attachment containing exactly the columns Purch id, Vendor code, Vendor name, Template id, Note, limited to the rows whose template resolves to that group.
8. **Given** one or more flagged purchase orders have no resolvable Alert group because they were flagged "Missing template id" (no template, so no group to resolve), **When** notifications are sent for the run, **Then** those purchase orders' rows are included in every one of that run's outgoing emails, in addition to each email's own group-specific rows.
9. **Given** no purchase order is flagged after a full run (every purchase order is fully complete), **When** notifications would otherwise be sent, **Then** no email is sent to any group and no Excel attachment is produced.
10. **Given** a distinct responsible Alert group has no configured recipient email addresses, **When** that group's email would otherwise be sent, **Then** the run continues processing other groups; the outcome for a group with no resolvable recipients is treated the same way as any other alert-delivery gap elsewhere in the system.
11. **Given** the missing-documentation store contains records left over from a previous run, **When** a new run starts, **Then** every existing record in the store is deleted before the first purchase order of the new run is evaluated.
12. **Given** a run has finished evaluating every purchase order and has recorded each flagged one in the store, **When** the per-group emails are built, **Then** their content (and the matching Excel attachment) is built from the store's current contents at that moment, not from data held only in memory during evaluation.

### User Story 3 - Push eligible local Templates and their active Vendor mappings out to the ERP (Priority: P1)

A Data Administrator needs the ERP system's own Template records to reflect the compliance Templates that have been finalized (Approved) locally, along with whichever vendor(s) each Template is currently mapped to (or none), so that ERP-side processes relying on ERP Template data see the same picture the compliance team maintains. Today the ERP has no automated way of learning about local Template changes. The administrator wants to trigger a synchronization action that, for every local Template that is active and Approved, first clears out that Template's existing ERP-side record(s) and then pushes a fresh ERP record for each vendor currently mapped to that Template — or, when a Template currently has no active vendor mapping at all, a single record with a blank Vendor Code, so that Template is still represented in the ERP — so the ERP always ends the run holding exactly the current local picture — no more, no less.

**Why this priority**: This is the entire scope of the requested change — a one-shot outbound data push. Without it, the feature delivers no value for this update.

**Independent Test**: Trigger the synchronization action against a local Template population that includes a mix of eligible Templates (active, Approved) with one active vendor mapping, with multiple active vendor mappings, with no active vendor mapping, and Templates that are excluded by eligibility (Draft status, hidden, or deleted). Confirm that after the run, the ERP received exactly one removal request per eligible Template and exactly one push per eligible Template's currently active vendor mapping — plus exactly one push with a blank Vendor Code for every eligible Template that has no currently active vendor mapping — with no push at all for ineligible Templates or for mappings whose effective date range does not cover today.

**Acceptance Scenarios**:

1. **Given** a local Template with IsDeleted = false, IsHide = false, and Status = Approved, **When** the synchronization action runs, **Then** the system requests the ERP remove any existing ERP-side record for that Template's Code before pushing any new data for it.
2. **Given** a local Template that is deleted, hidden, or not yet Approved (Status = Draft), **When** the synchronization action runs, **Then** that Template is excluded entirely — no ERP removal request and no push are made for it.
3. **Given** an eligible Template (from Scenario 1) has a Vendor mapping whose configured effective date range (From Date through To Date) includes the current date, **When** the synchronization action runs, **Then** the system pushes one record to the ERP for that Template, carrying the Template's Code, the Template's Name, and that mapping's Vendor Code.
4. **Given** an eligible Template has a Vendor mapping whose effective date range does not include the current date (expired or not yet started), **When** the synchronization action runs, **Then** no push is made for that mapping.
5. **Given** an eligible Template has more than one currently active Vendor mapping, **When** the synchronization action runs, **Then** one separate push is made per active mapping, each carrying the same Code and Name but that mapping's own Vendor Code.
6. **Given** an eligible Template has zero currently active Vendor mappings (none configured, or none whose date range covers today), **When** the synchronization action runs, **Then** the ERP removal request from Scenario 1 still happens for it, and the system pushes exactly one record for it to the ERP carrying that Template's Code, that Template's Name, and a blank Vendor Code — the Template ends the run with exactly one ERP-side record, not zero (updated 2026-08-17 — previously no push occurred for a Template with zero active mappings, leaving it with no ERP-side record; see Assumptions).
7. **Given** the ERP source spans more eligible Templates or active mappings than fit in a single processing batch, **When** the synchronization action runs, **Then** every eligible Template and every one of its currently active mappings (or its single blank-Vendor-Code push, per Scenario 6) is processed before the run finishes.
8. **Given** the synchronization action has already been run once with no changes to local Template or Vendor-mapping data since, **When** it is run again, **Then** the ERP ends up holding the same set of records as after the first run (the removal-then-push pattern makes every run converge to the same result, not accumulate duplicates).

### Edge Cases

- What happens when the ERP reference data contains multiple records for the same sales order (e.g., two different purchase orders under the same sales order) within a single run? Only the first one encountered is added; subsequent records for that same sales order are treated as already existing and skipped, since the "already exists" check runs against the same table being written to.
- What happens when a reference record is missing a sales order ID, purchase order ID, or template code? That record is skipped — it cannot form a valid mapping record.
- What happens when the ERP reference data is empty? The synchronization completes successfully having added zero records.
- What happens when the ERP source is temporarily unavailable or returns an error mid-run? The run stops and reports failure; records already added before the failure remain (no automatic rollback), and a subsequent run can be attempted, skipping the sales orders already synced.
- What happens when a purchase order's compliance template value does not match any configured template? "No PO folder" cannot apply (there is no step list to check against), so the run flags it "Missing template id" — the same outcome as an empty template value, since neither case yields a usable template to check steps against.
- What happens when the same purchase order ID appears more than once in the ERP purchase-order reference data within one run? Each occurrence is evaluated independently; if any occurrence is flagged, the purchase order can appear more than once in the report with potentially different notes, since this check does not de-duplicate by purchase order ID.
- What happens when a template has no document steps configured at all? A purchase order using that template, once its folder is confirmed to exist, has no steps to check and is therefore not flagged for missing steps (its note stays empty unless it was already flagged earlier for a missing template or folder).
- What happens if the ERP purchase-order source or the SharePoint folder check is temporarily unavailable mid-run? Consistent with User Story 1's failure handling, the run stops and reports failure rather than sending a partial or misleading report; a subsequent run can be retried.
- What happens when a purchase order's vendor code or vendor name is not available from the ERP reference data? The report still includes the row with whatever vendor fields are available (blank where missing) — a missing vendor field does not by itself prevent the purchase order from being evaluated or flagged.
- What happens when the store is cleared at the start of a run and then every purchase order evaluated in that run turns out fully complete? The store ends up completely empty (nothing survives the clear, nothing new is added), and no email is sent (FR-018) — this is not treated as an error.
- What happens if the check is triggered again while a previous run is still in progress? Out of scope for this feature; concurrent runs are not guarded against, consistent with how User Story 1 and the existing `compl-sales-order-missing` feature (009) treat this same scenario.
- What happens to a record's Alert group value in the store when the purchase order was flagged "Missing template id"? It is stored as blank/absent (no group was resolved), consistent with that finding being included in every group's email for the run rather than being tied to one specific group.
- What happens when an eligible Template (User Story 3) has never had any Vendor mapping at all? It is treated the same as having zero currently active mappings — its existing ERP record is removed and then exactly one record is pushed for it with a blank Vendor Code (updated 2026-08-17).
- What happens when an eligible Template has two active Vendor mappings for the same Vendor Code with overlapping effective date ranges? Both mappings are currently active per the date check, so the system does not de-duplicate — one push is sent per mapping row, potentially two pushes carrying an identical Code/Name/VendorCode.
- What happens when an eligible Template's Name is blank? The push still proceeds with whatever Name value is available (blank if that's what local data holds) — a blank Name does not by itself exclude the Template or its mappings from being pushed.
- What happens if the ERP is temporarily unavailable or returns an error partway through a synchronization run (User Story 3)? Consistent with User Story 1 and User Story 2's failure handling, the run stops and reports failure; any removal or push requests already sent to the ERP before the failure remain in effect (no automatic rollback), and a subsequent run can be retried.
- What happens if the synchronization action (User Story 3) is triggered again while a previous run is still in progress? Out of scope for this feature; concurrent runs are not guarded against, consistent with how User Story 1 and User Story 2 treat this same scenario.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a manually triggerable synchronization action that retrieves the full set of Sales Order Template reference records from the ERP reference data source (reference type: Sales Order Templates), across all pages of that source.
- **FR-002**: For each retrieved reference record, system MUST derive a candidate mapping record's Sales Order ID, Purchase Order ID, and Template Code from that record's Sales Order, Purchase Order, and Template values respectively.
- **FR-003**: Before creating a mapping record, system MUST check whether a mapping record already exists for that Sales Order ID.
- **FR-004**: System MUST skip creating a mapping record (no insert, no update) whenever a mapping record already exists for that Sales Order ID.
- **FR-005**: System MUST create a new mapping record only when no mapping record currently exists for that Sales Order ID.
- **FR-006**: System MUST skip any retrieved reference record that is missing a Sales Order ID, Purchase Order ID, or Template Code, without creating a mapping record for it.
- **FR-007**: System MUST report the outcome of a synchronization run (at minimum: success/failure, and counts of records added vs. skipped) back to the caller who triggered it.
- **FR-008**: System MUST restrict the synchronization action to authenticated/authorized callers, consistent with other administrative actions in the system.

- **FR-009**: System MUST provide a second, independently triggerable check that retrieves the full set of Purchase Order reference records from the ERP reference data source (reference type: Purchase Orders), across all pages of that source, evaluating every record retrieved.
- **FR-010**: For each retrieved purchase order, System MUST flag it with the note "Missing template id" — and perform no further check for it — whenever that purchase order has no compliance template value recorded (including when its recorded value does not match any configured template).
- **FR-011**: For each retrieved purchase order that has a compliance template value recorded, System MUST check whether a document folder named exactly after that purchase order's ID already exists at the system's configured EUTR document storage location, and MUST flag it with the note "No PO folder" — performing no further check for it — whenever that folder does not exist.
- **FR-012**: For each retrieved purchase order that has a compliance template value recorded and an existing document folder, System MUST retrieve the ordered list of document steps configured on that purchase order's template (from Template Management) and, for each step, determine whether at least one document has already been recorded for that purchase order under that step (from Document Management).
- **FR-013**: System MUST flag a purchase order (from FR-012) with one note line per step found to have no recorded document, in the form "{n} - {step name} - Missing", where the step name comes from Step Management (001-eutr-steps) and `n` is sequential (starting at 1) among that purchase order's own missing steps, in the order those steps are configured on the template; a purchase order with every step already covered MUST NOT be flagged.
- **FR-014**: System MUST exclude from the store, from the report, and from every outgoing email any purchase order that was not flagged (no note) during evaluation — only flagged purchase orders (FR-010, FR-011, FR-013) are ever stored, reported, or emailed.
- **FR-015**: System MUST resolve, for each flagged purchase order that has a compliance template, that template's configured responsible Alert group; purchase orders flagged "Missing template id" have no resolvable Alert group.
- **FR-016**: System MUST send one separate email per distinct Alert group resolved in a run (FR-015), each containing only the flagged purchase orders whose template resolves to that group, plus every purchase order flagged "Missing template id" in that same run (FR-010) regardless of group.
- **FR-017**: Each email in FR-016 MUST include exactly one Excel attachment containing the same rows as that email's content, with exactly the columns Purch id, Vendor code, Vendor name, Template id, Note, in that order.
- **FR-018**: System MUST NOT send any email or produce any Excel attachment when no purchase order is flagged in a run.
- **FR-019**: System MUST restrict this check to authenticated/authorized callers, consistent with FR-008 and other administrative actions in the system.
- **FR-020**: Before evaluating any purchase order in a run, System MUST delete every existing record in the purchase-order missing-documentation store, so no record from a previous run persists into the current one.
- **FR-021**: For each flagged purchase order (FR-014), System MUST insert one record into the purchase-order missing-documentation store, carrying that purchase order's ID, vendor code, vendor name, template identifier, computed note, and resolved Alert group (blank/absent when flagged "Missing template id").
- **FR-022**: After every purchase order has been evaluated and the store has been fully repopulated for the run, System MUST build each Alert group's email (FR-016) and Excel attachment (FR-017) from the store's current contents at that point, not from data held only in memory during evaluation.

- **FR-023**: System MUST provide a third, independently triggerable synchronization action that pushes eligible local Template data, and each eligible Template's currently active Vendor mappings, out to the ERP system.
- **FR-024**: System MUST determine the eligible Template population as every local Template record that is not deleted, not hidden, and in Approved status (IsDeleted = false, IsHide = false, Status = Approved).
- **FR-025**: For every eligible Template (FR-024), before pushing any new data for it, System MUST request the ERP system remove any existing ERP-side Template record matching that Template's Code — this removal step MUST complete for every eligible Template before the push step (FR-027) begins for any of them.
- **FR-026**: After the removal step (FR-025) has completed, System MUST determine, for each eligible Template, its currently active Vendor mappings via a left join from eligible Templates to Vendor mappings — the ones whose configured effective date range (From Date through To Date) includes the current date — such that a Template with zero currently active Vendor mappings still yields exactly one join result for that Template, with a blank Vendor Code, rather than zero results (updated 2026-08-17 — previously a Template with zero currently active Vendor mappings yielded no join result and consequently no push; see FR-028 and Assumptions).
- **FR-027**: For each of an eligible Template's join results from FR-026, System MUST push one record to the ERP system carrying that Template's Code, that Template's Name, and that result's Vendor Code (blank when the Template has no currently active Vendor mapping, per FR-026's left join).
- **FR-028**: An eligible Template with zero currently active Vendor mappings MUST still have exactly one record pushed to the ERP system for that run, carrying a blank Vendor Code (FR-026/FR-027) — every eligible Template MUST be represented in the ERP by at least one pushed record every run, never left with zero (updated 2026-08-17 — previously this Template received no push at all and was left without any ERP-side record; see Assumptions).
- **FR-029**: System MUST report the outcome of a synchronization run (at minimum: success/failure, count of eligible Templates processed, count of ERP push records sent) back to the caller who triggered it.
- **FR-030**: System MUST restrict this synchronization action to authenticated/authorized callers, consistent with FR-008 and FR-019.

### Key Entities

- **Sales Order Template Reference (ERP source data)**: A record from the ERP reference data representing a link between a sales order, a purchase order, and a compliance template. Key attributes: Sales Order ID, Purchase Order ID, Template Code.
- **Purchase Attachment Mapping (local record)**: The local record that associates a Sales Order ID with a Purchase Order ID and a Template Code, used elsewhere in the system to determine which compliance template applies to a sales order. Uniqueness is keyed on Sales Order ID for the purposes of this synchronization (one mapping record is created per distinct new Sales Order ID per run).
- **Purchase Order Reference (ERP source data, User Story 2)**: A record from the ERP reference data representing one purchase order. Key attributes used by this check: Purchase Order ID, Vendor code, Vendor name, and the compliance template value (if any) recorded against it.
- **Compliance Template Step Configuration (existing — Template Management)**: The ordered list of document steps configured on a compliance template, read-only from this check. Key attributes: each step's name (from Step Management, 001-eutr-steps), its configured order/position, and the Alert group configured on the template — used to resolve FR-012/FR-013 and FR-015/FR-016.
- **Recorded Compliance Document (existing — Document Management)**: A document already uploaded and associated with a specific purchase order and a specific template step, read-only from this check. Used only to determine, per purchase order and step, whether at least one such document exists (FR-012).
- **Purchase-Order Missing-Documentation Record (local, persisted)**: The stored result of evaluating one flagged purchase order — Purchase Order ID, Vendor code, Vendor name, Template identifier, computed Note (exactly one of: "Missing template id", "No PO folder", or one-or-more "{n} - {step name} - Missing" lines, `n` sequential among that purchase order's own missing steps), and the resolved Alert group (blank/absent for a "Missing template id" record, since no template means no group to resolve). Every run first deletes every existing record in this store (FR-020), then inserts one record per flagged purchase order found during that run (FR-021) — the store always reflects only the most recent run's results, never a mix of runs, and never contains a record for a purchase order that was fully complete. This store is the source the per-group emails and Excel attachments are built from (FR-022), not an in-memory list kept only for the duration of the run.
- **Template (existing local record — 003-eutr-templates)**: The compliance Template record read (not modified) by this action. Key attributes used here: Code, Name, IsDeleted, IsHide, Status (Draft/Approved) — used to determine eligibility (FR-024) and to populate each ERP push (FR-027).
- **Template Vendor Mapping (existing local record — 003-eutr-templates "Apply to Customer/Vendor")**: The record linking a Template to a Vendor for a specific effective date range (From Date, To Date), read (not modified) by this action. Used to determine each eligible Template's currently active Vendor(s) via a left join (FR-026) and to supply the Vendor Code for each ERP push (FR-027) — a Template with no matching mapping row still yields one push with a blank Vendor Code (updated 2026-08-17).
- **ERP Template Record (external, ERP-side)**: The Template record held by the ERP system, identified there by Template Code. This action removes the ERP-side record(s) for each eligible Template (FR-025) and then recreates one ERP-side record per that Template's currently active Vendor mapping — or exactly one record with a blank Vendor Code when the Template has none (FR-026/FR-027/FR-028, updated 2026-08-17). Not read back or stored locally by this feature — this action only writes to it.

## Assumptions

- This synchronization is a manually-triggered, test-oriented action (reflected by the endpoint's "test" naming) rather than a scheduled/automatic background job; adding scheduling is out of scope for this feature.
- The synchronization is one-directional: from the ERP reference data into the local mapping table. It does not update, delete, or reconcile local mapping records that no longer match the ERP source.
- "Already exists" is evaluated strictly by Sales Order ID — if a mapping record already exists for a Sales Order ID with a different Purchase Order or Template than the current ERP source data, it is left as-is (no update), matching the explicit "skip if exists" instruction.
- The ERP reference data source used for reference type 19 already returns the Sales Order ID, Purchase Order ID, and Template Code fields needed; no changes to that source are required by this feature.
- Errors from the ERP reference data source during a run are surfaced as a failed run rather than being silently swallowed, since the administrator needs to know whether the full dataset was processed.
