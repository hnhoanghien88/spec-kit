## Summary

Add a new backend-only alert job to the existing compliance-sys-api that, on demand, re-evaluates every open sales order's compliance status, persists a fresh "missing compliance" snapshot, and sends one consolidated email + in-app notification. The feature clones the existing `ComplNotificationController.TestAlert` / `ComplNotificationService.SendAlertAsync` pattern exactly (same controller, same service class), adding a new endpoint `GET api/notification/test-sales-order-alert` and a new method `SendSalesOrderAlertAsync`. It orchestrates two already-existing application services (`IComplDynamicsService.GetDynRefePagedAsync` for the open sales order list, `IViewCompliancesService.GetViewCompliancesAsync` for the per-sales-order compliance check) and a persistence path for `compl_so_missing` (table previously defined in SQL but with zero C# usage before this feature) plus a mail/notification method mirroring the existing `SendMailAndNotification` private helper.

**2026-08-04 update**: This feature was already implemented once (Phase 1–4 tasks in `tasks.md` are checked off) using a **per-`SalesId` delete-before-insert** pattern: `IComplSoMissingRepository.DeleteBySalesIdAsync(so.Code, ct)` was called inside the per-sales-order loop, immediately before that sales order's `InsertManyAsync`. The spec was revised to remove that logic entirely and replace it with a **single delete-all step run once, before the loop starts** (`spec.md` FR-006, Edge Cases). This plan update reflects that change: `DeleteBySalesIdAsync` is removed from the repository interface/implementation, a new `DeleteAllAsync()` method is added, and `RefreshSalesOrderMissingComplianceAsync` calls it exactly once before entering the open-sales-order loop instead of once per sales order inside the loop.

**2026-08-10 update**: Per the revised spec.md (FR-012–FR-014, SC-005), the alert email built by the already-implemented `ComplNotificationService.SendMailAndNotificationForSalesOrderMissing` (`ComplianceSys.Application/Services/ComplNotificationService.cs:763-793`) is revised to (1) show a fixed 14-column layout — `SalesId, MasterCode, MasterName, Status, Code, Name, ValidFrom, ValidTo, DaysRemaining, ResponsibleEmails, Description, MappedRefTypeCode, MappedInputValue, MappedRefTypeName` — replacing today's 9-column layout (which lacks `Status`, `DaysRemaining`, `ResponsibleEmails`, and shows `MappedInputValue`/`MappedRefTypeName` under the labels "Value"/"Value name" instead of "Product"/"Product name", and has no `MappedRefTypeCode`/"Type" column at all), and (2) compute `Status` ("Missing"/"Expired"/"Valid") and `DaysRemaining` ("N days left" / "-N days left" / blank) per row, at send time, from that row's own `Code`/`ValidTo`, instead of reusing the entity's stored `Status` (always the literal `"MISSING"` per FR-005) or leaving `DaysRemaining` absent (the `compl_so_missing` table and `ComplSoMissingResponseDto` have no `DaysRemaining` column at all — see data-model.md). This is a display-only change scoped entirely to the anonymous projection and `customHeaders` dictionary inside `SendMailAndNotificationForSalesOrderMissing`, plus two new small private helper methods; it does not touch `ComplSoMissing`, `ComplSoMissingResponseDto`, the repository, or `RefreshSalesOrderMissingComplianceAsync`. **Status: implemented** (T023–T026).

**2026-08-10 update (Excel attachment)**: Per the further-revised spec.md (FR-015–FR-017, SC-006), `SendMailAndNotificationForSalesOrderMissing` now also generates an Excel workbook mirroring the same `complianceList`/`customHeaders` used for the HTML email table (the 14-column layout above), and adds it as an unconditional `AttachmentInfo` (`Type = AttachmentType.Stream`) to the same `attachments` list already passed to `mailAlert.SendMailV2(...)` — independent of, and in addition to, the existing `Mail.SendAttachment`-gated per-row SharePoint file attachments in that same method. The workbook is built with **ClosedXML** (`ComplianceSys.Application.csproj` already references `ClosedXML 0.102.3`; no new package needed), following the exact from-scratch-workbook pattern already used by `EutrMastersExportService.ExportToExcelAsync` (`new XLWorkbook()` → add a worksheet → header row → data rows → `SaveAs(MemoryStream)` → `byte[]`) — see research.md R9. The file is named `compl-sales-order-missing-<yyyyMMddHHmmss>.xlsx` using the moment the alert is generated (`DateTime.Now`, matching the existing codebase's non-UTC convention for user-facing timestamps in this file, e.g. `DateTime.Today` used by T023/T024's Status/Days-remaining computation).

**2026-08-18 update (deduplicate alert rows, drop Sales order column)**: Per the further-revised spec.md (FR-008, FR-012, SC-007), the read-back step in `SendSalesOrderAlertAsync` (`ComplNotificationService.cs:176-206`) that builds `alertCompliances` from `_complSoMissingRepository.GetAllAsync()` now deduplicates the returned rows by the combination of `MasterCode`, `Code`, `MappedRefTypeCode`, `MappedInputValue` (`Enumerable.DistinctBy`, first-occurrence-wins, applied to the raw `ComplSoMissing` rows before the existing `ComplSoMissingResponseDto` projection) before that same list is passed into `SendMailAndNotificationForSalesOrderMissing` — so both the email/Excel content and the in-app `ComplNotification` records this method already builds are based on the deduplicated set (research.md R11). Separately, inside `SendMailAndNotificationForSalesOrderMissing`, the `complianceList` anonymous projection drops `c.SalesId` and `customHeaders` drops the `{"SalesId", "Sales order"}` entry (13-column layout, was 14), so the Sales order column no longer appears in either the email body or the Excel attachment (research.md R11). This is scoped entirely to `SendSalesOrderAlertAsync`'s read-back step and the `complianceList`/`customHeaders` in `SendMailAndNotificationForSalesOrderMissing`; it does not touch `ComplSoMissing`, `ComplSoMissingResponseDto` (still carries `SalesId`, used unchanged by the notification-message text later in the same method), the repository, `RefreshSalesOrderMissingComplianceAsync`, the controller, or the schema.

**2026-08-20 update (highlight Expired rows yellow in the Excel attachment)**: Per the further-revised spec.md (FR-018, SC-008), the email body already highlights each row whose Status is "Expired" with a yellow background (`Helper.GenerateHtmlTableValidTo`, `Helper.cs:244`, `#fff59d`); the Excel attachment does not. `BuildSalesOrderMissingExcelAttachment` (`ComplNotificationService.cs:427-464`, research.md R9) is revised to apply the identical `#fff59d` fill, via ClosedXML's `Style.Fill.BackgroundColor = XLColor.FromHtml("#fff59d")`, to the full cell range of any row whose already-computed `Status` (read from the same `complianceList` item already used for that row's cell values, per R8) equals `"Expired"` — following the same `sheet.Range(row, ...).Style.Fill.BackgroundColor` pattern already used elsewhere in this codebase for row highlighting (`ComplComplianceImportService.cs:951-954`, research.md R12). This is scoped entirely to `BuildSalesOrderMissingExcelAttachment`'s row-writing loop; it does not touch the email body's own highlighting (`Helper.cs:244`, unchanged), `ComplSoMissing`, `ComplSoMissingResponseDto`, the repository, `RefreshSalesOrderMissingComplianceAsync`, the controller, or the schema — and needs no new NuGet package (`XLColor` is already part of the referenced ClosedXML package).

**2026-08-20 update (re-add a combined Sales order column)**: Per the further-revised spec.md (FR-008, FR-012, FR-019, SC-007, SC-009), a Sales order column is reintroduced as the **last** column in both the email body and the Excel attachment (superseding the 2026-08-18 removal). Because the alert's rows are grouped by Master code/Code/Type/Product, this column now shows every distinct sales order code collapsed into that group, combined (e.g. "SO1, SO2") — not a single sales order like the original pre-2026-08-18 layout. In `SendSalesOrderAlertAsync` (`ComplNotificationService.cs:173-224`), the read-back's `.DistinctBy(...)` becomes `.GroupBy(...)` on the same key, and a new `CombinedSalesIds` property on `ComplSoMissingResponseDto` (`Dtos/Response/ComplSoMissingResponseDto.cs`) is populated per group as `string.Join(", ", distinct SalesIds in that group)` (research.md R13). In `SendMailAndNotificationForSalesOrderMissing`, `complianceList`/`customHeaders` gain one new last entry, `SalesOrder = c.CombinedSalesIds` / `{"SalesOrder", "Sales order"}`. `ComplSoMissingResponseDto.SalesId` itself is unchanged (still the group's first-occurrence single sales order code) and continues, unmodified, to drive the per-recipient in-app notification message text later in the same method — this update is scoped to the email/Excel columns only, per the user's own request wording ("bảng nội dung email và file excel").

## Technical Context

**Language/Version**: C# / .NET 8 (matches all four existing projects: `ComplianceSys.Api`, `ComplianceSys.Application`, `ComplianceSys.Domain`, `ComplianceSys.Infrastructure`)

**Primary Dependencies**: ASP.NET Core Web API, Dapper via `Res.Shared.Dapper` (v1.0.5, provides `DapperRepository<TEntity,TKey>`, `IUnitOfWork`, `IRepository<,>`), AutoMapper, FluentValidation, Hangfire (background jobs, used elsewhere in this controller but not required for this feature), Serilog (static `Log`), Newtonsoft `JsonConvert` (JSON group-email parsing), **ClosedXML 0.102.3** (2026-08-10 Excel-attachment update — already referenced by `ComplianceSys.Application.csproj` for other exports, e.g. `EutrMastersExportService`; no new package added)

**Storage**: MySQL (existing `compl_so_missing` table already defined in `compliance-sys-api/src/ComplianceSys.Infrastructure/Sqls/Tables/compl_so_missing.sql`, currently unused by any C# code)

**Testing**: xUnit 2.9.2 + Moq 4.20.72, in `compliance-sys-api/tests/ComplianceSysApi.UnitTests`

**Target Platform**: ASP.NET Core Web API (existing `ComplianceSys.Api` host), Windows/Linux server

**Project Type**: Backend-only addition to an existing Clean Architecture web service (no frontend work; this is an internal/testing-triggered alert job, not a user-facing screen)

**Performance Goals**: No new hard target beyond the existing alert flow's expectations; the job runs on demand (manual trigger), so it is not on a user-facing request path. Each sales order is checked sequentially, matching the existing per-master loop style in `SendMailAndNotificationByMasterDefaultCreateAsync`.

**Constraints**: Must reuse `IComplDynamicsService` and `IViewCompliancesService` exactly as they exist today (Constitution Principle III); must not duplicate their query logic. Must not break the existing `test-alert` / `SendAlertAsync` flow.

**Scale/Scope**: Bounded by the number of currently open sales orders returned by the Dynamics reference lookup (paged; expected low hundreds based on existing "Open order" sales order volumes in this system).
