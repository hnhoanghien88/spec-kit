## User Scenarios & Testing *(mandatory)*

### User Story 1 - Refresh the missing-compliance snapshot for every open sales order (Priority: P1)

A Compliance Admin (or a support engineer testing the alert pipeline) triggers a check that first clears the entire missing-compliance store, then walks every currently open sales order, re-evaluates its compliance status, and repopulates the store with exactly the compliance items still missing for each sales order evaluated in that run.

**Why this priority**: This is the data foundation the alert depends on. Without an accurate, current snapshot of what is missing per sales order, no meaningful alert can be sent — this must exist and be correct before notification is worth building.

**Independent Test**: Can be fully tested by triggering the check and then inspecting the missing-compliance store: the store contains no records left over from before the run started, every currently open sales order has been evaluated, and for each one the stored missing items match exactly what its compliance lookup reported as MISSING during this run (no sales order skipped).

**Acceptance Scenarios**:

1. **Given** a set of open sales orders exists, **When** the check is triggered, **Then** the system first deletes every existing record in the missing-compliance store, then retrieves the full list of open sales orders and evaluates every one of them before finishing.
2. **Given** an open sales order currently has one or more compliance items with status MISSING, **When** that sales order is evaluated, **Then** those MISSING items (and only those) are stored against that sales order's code in the missing-compliance store.
3. **Given** an open sales order previously had missing items recorded from an earlier run, **When** the current run's initial clear step runs and it is then re-evaluated and found fully compliant (no items with status MISSING), **Then** none of its old missing-compliance records survive the clear step and no new ones are added for it.
4. **Given** an open sales order previously had missing items recorded, **When** the current run's initial clear step removes all prior records and it is then re-evaluated and still has some (possibly different) items missing, **Then** only the current set of MISSING items is stored for that sales order — no rows from the previous run remain.
5. **Given** the list of open sales orders is empty, **When** the check is triggered, **Then** the system still deletes every existing record in the missing-compliance store, no sales order is evaluated, and the store ends up empty.
6. **Given** an open sales order has no delivery date recorded, or its delivery date equals the source system's "no date recorded" placeholder value, **When** that sales order is evaluated, **Then** its compliance lookup (FR-004) uses today's date as the check date, the same way the compliance screen does when opened for that sales order without an explicit date filter — not the placeholder date.
7. **Given** an open sales order has a genuine, non-placeholder delivery date recorded, **When** that sales order is evaluated, **Then** its compliance lookup continues to use that delivery date as the check date, unchanged from prior behavior.
8. **Given** an open sales order and a compliance master whose validity window has already started as of today but had not started as of the source system's "no date recorded" placeholder value, **When** that sales order is evaluated, **Then** that master is correctly recognized as currently valid and is not stored as missing for that sales order — matching what the compliance screen shows for the same sales order and master on the same day.

### User Story 2 - Notify responsible stakeholders after the snapshot is refreshed (Priority: P2)

After the missing-compliance snapshot has been refreshed for all open sales orders, the system sends a single consolidated alert (email plus in-app notification) summarizing every sales order that currently has missing compliance items, so responsible stakeholders know what needs attention.

**Why this priority**: Notification is the payoff of the check — it depends on User Story 1 having produced an accurate snapshot, but is a distinct, separately verifiable step (the alert content and delivery can be checked against the stored snapshot independently of how that snapshot was produced).

**Independent Test**: Can be fully tested by ensuring the missing-compliance store already contains known records, triggering (or resuming) the notification step, and confirming exactly one alert is sent whose content matches every current record in the store.

**Acceptance Scenarios**:

1. **Given** the missing-compliance store contains one or more records after a refresh, **When** the notification step runs, **Then** exactly one alert (email plus in-app notification) is sent that lists every current record, addressed to the same responsible/alert recipients used by other compliance alerts in the system.
2. **Given** the missing-compliance store is empty after a refresh (no sales order currently has missing items), **When** the notification step runs, **Then** no alert is sent.
3. **Given** a manual/test trigger for this feature (mirroring the existing manual compliance-alert test trigger), **When** an administrator or tester invokes it, **Then** the full refresh-then-notify process described in User Story 1 and this story runs end-to-end on demand.
4. **Given** the alert is being composed from the current set of missing-compliance records, **When** the alert content is generated, **Then** it presents, for every record, exactly these columns in this order: Master code, Master name, Status, Code, Name, Valid from, Valid to, Days remaining, Responsible emails, Description, Type, Product, Product name, Sales order — Sales order is the last column.
5. **Given** a record in the current set has no Code recorded, **When** the alert content is generated, **Then** that record's Status column shows "Missing".
6. **Given** a record in the current set has a Code recorded and its Valid To date is earlier than the date the alert is generated, **When** the alert content is generated, **Then** that record's Status column shows "Expired".
7. **Given** a record in the current set has a Code recorded and either has no Valid To date or has a Valid To date that is not earlier than the date the alert is generated, **When** the alert content is generated, **Then** that record's Status column shows "Valid".
8. **Given** a record in the current set has no Valid To date, **When** the alert content is generated, **Then** that record's Days remaining column is left blank.
9. **Given** a record in the current set has a Valid To date that is 10 days after the date the alert is generated, **When** the alert content is generated, **Then** that record's Days remaining column reads "10 days left".
10. **Given** a record in the current set has a Valid To date that is 5 days before the date the alert is generated, **When** the alert content is generated, **Then** that record's Days remaining column reads "-5 days left".
11. **Given** the alert email is about to be sent, **When** it is sent, **Then** it includes exactly one Excel file attachment containing the same columns, in the same order, and the same row data (including the computed Status and Days remaining values) as the email body.
12. **Given** the alert email is generated at a specific moment in time, **When** the Excel attachment is named, **Then** its file name follows the pattern `compl-sales-order-missing-<yyyyMMddHHmmss>`, where the timestamp reflects the moment the alert was generated.
13. **Given** the missing-compliance store is empty after a refresh and no alert email is sent (Acceptance Scenario 2), **When** the notification step runs, **Then** no Excel attachment is produced either.
14. **Given** the missing-compliance store contains two or more records that share the same Master code, Code, Type, and Product but were captured against different sales orders, **When** the current set of records is read to build the alert, **Then** those records are collapsed into a single row in both the email body and the Excel attachment, so each distinct Master code/Code/Type/Product combination appears exactly once.
15. **Given** a record in the current set has Status = "Expired", **When** the Excel attachment is generated, **Then** that record's row in the Excel file is highlighted with the same yellow background color already used for that record's row in the email body.
16. **Given** a record in the current set has Status = "Missing" or "Valid", **When** the Excel attachment is generated, **Then** that record's row in the Excel file is left with no yellow highlight, matching the email body's treatment of non-Expired rows.
17. **Given** two or more missing-compliance records share the same Master code, Code, Type, and Product (Acceptance Scenario 14) but were captured against different sales orders — e.g. "SO1" and "SO2", **When** those records are collapsed into a single alert row, **Then** that row's Sales order column shows every distinct sales order code from the collapsed records combined into one cell, in the form "SO1, SO2".
18. **Given** a group of missing-compliance records that collapse into a single alert row came from only one underlying sales order, **When** the alert content is generated, **Then** that row's Sales order column shows just that one sales order code, with no separator or list formatting.
19. **Given** two records collapsed into the same alert row were both captured against the same sales order code (e.g. inserted twice for that code in the same run, per the duplicate-open-sales-order Edge Case), **When** that row's Sales order column is built, **Then** that sales order code appears only once in the combined value, not repeated.
20. **Given** the Excel attachment is being generated, **When** its header row (the row of column titles) is written, **Then** that row is styled with the same background color, bold text, and cell borders already used for the header row in the email body, so a reader sees a matching header regardless of which representation of the alert they open.
21. **Given** the test-sales-order-alert trigger (FR-001) is about to send its alert, **When** the email is addressed and the in-app notification recipients are determined, **Then** no email address belonging to the Alert emails recipient group is included, in either the To/Cc line of the email or the in-app notification recipients, for that send.
22. **Given** the test-sales-order-alert trigger excludes the Alert emails group (Acceptance Scenario 21) and the Responsible emails group for the current set of records is non-empty, **When** the alert is sent, **Then** it is still sent to the Responsible emails group as before, and its content (columns, Responsible emails column value, Status/Days remaining, highlighting) is unchanged by the exclusion.

### User Story 3 - Diagnose alert content using a Sales-order-free variant (Priority: P3)

A support engineer testing the alert pipeline triggers a second, diagnostic-only entry point that runs the exact same refresh-and-notify process as User Story 1 and User Story 2, except that the Sales order column is entirely omitted from both the email body and the Excel attachment for that run's alert.

**Why this priority**: This is a lower-priority, test-only variant of an already-working alert; it exists purely so a tester can inspect the alert's other columns without the Sales order column's combined-values noise, and it only makes sense to build once User Story 1 and User Story 2 already produce a correct, complete alert.

**Independent Test**: Can be fully tested by triggering this diagnostic entry point and confirming the missing-compliance store is refreshed and one alert (email plus Excel attachment) is sent identically to the existing test-sales-order-alert trigger, except that the Sales order column is absent from both the email table and the Excel attachment — while every other column, computed value, highlight, and style is unchanged.

**Acceptance Scenarios**:

1. **Given** a set of open sales orders exists and produces one or more current missing-compliance records, **When** the diagnostic trigger runs, **Then** it performs the same refresh (User Story 1) and read-back-and-dedup (FR-008) steps as the existing test-sales-order-alert trigger, and sends exactly one consolidated alert (email plus in-app notification) built from that same current set of records.
2. **Given** the diagnostic trigger's alert is being composed, **When** its email body is generated, **Then** it presents the same 13 columns and order as FR-012 minus Sales order (Master code, Master name, Status, Code, Name, Valid from, Valid to, Days remaining, Responsible emails, Description, Type, Product, Product name), with the Sales order column omitted entirely rather than shown empty.
3. **Given** the diagnostic trigger's alert is being composed, **When** its Excel attachment is generated, **Then** it mirrors the same 13 columns as its own email body (Sales order omitted), matching each other record-for-record, consistent with FR-015.
4. **Given** the diagnostic trigger's alert is generated, **When** Status, Days remaining, Expired-row highlighting, and the Excel header styling are applied, **Then** they are computed and applied exactly as in the existing test-sales-order-alert trigger (FR-013, FR-014, FR-018, FR-022), unaffected by the Sales order column being omitted.
5. **Given** the current set of missing-compliance records is empty after a refresh, **When** the diagnostic trigger runs, **Then** no alert and no Excel attachment are sent, the same no-alert-when-empty rule (FR-010) that governs the existing trigger.
6. **Given** the diagnostic trigger is invoked, **When** it runs, **Then** it does not change the `compl_so_missing` store's population logic, the existing test-sales-order-alert trigger, or any other existing alert — it is an additional, separate manual entry point only.
7. **Given** the diagnostic trigger's alert is generated, **When** its title (email subject and the heading shown above the table in the email body) is set, **Then** it reads "Missing compliance Information" instead of "Sales orders with missing compliance", since the alert's content is no longer tied to individual sales orders; the existing test-sales-order-alert trigger's title is unaffected.
8. **Given** the diagnostic trigger (FR-023) is about to send its alert, **When** the email is addressed and the in-app notification recipients are determined, **Then** no email address belonging to the Responsible emails recipient group is included, in either the To/Cc line of the email or the in-app notification recipients, for that send.
9. **Given** the diagnostic trigger excludes the Responsible emails group (Acceptance Scenario 8) and the Alert emails group for the current set of records is non-empty, **When** the alert is sent, **Then** it is still sent to the Alert emails group as before, and its content (columns, Responsible emails column value shown as data, Status/Days remaining, highlighting, title) is unchanged by the exclusion.

### Edge Cases

- What happens when the open sales order list contains the same sales order code more than once? Because the store is cleared once up front rather than per sales order code, each occurrence in the list is evaluated and inserted independently; if the same code appears more than once, its MISSING items from every occurrence accumulate in the store for that run rather than the later occurrence replacing the earlier one.
- What happens if the compliance lookup for one specific sales order fails or returns an error? Because the entire store was already cleared before evaluation began, that sales order simply has no missing-compliance records for this run (there is nothing left over to fall back to); it will be represented again only once its lookup succeeds in a later run. The system continues evaluating the remaining sales orders rather than aborting the whole run.
- What happens if a sales order in the open list is missing an expected field (e.g., no delivery date or customer account)? The system still runs the compliance lookup with whatever values are available, since the lookup already tolerates optional filters.
- What happens if the check is triggered again while a previous run is still in progress? Out of scope for this feature; concurrent runs are not guarded against.
- What happens when no sales orders currently have any MISSING compliance items, even though open sales orders exist? The store was already cleared at the start of the run, every sales order is still evaluated, and since none of them contributes any MISSING item, the store ends up empty and no alert is sent.
- What happens if a record's Valid To date is exactly the current date when the alert is generated? It is not earlier than the current date, so the record is treated as not yet expired (Status = "Valid", Days remaining = "0 days left").
- What happens if a record has a Code and a Valid To date that has already passed, given the store only holds records whose lookup reported MISSING (FR-005)? Its Status still displays as "Expired" rather than "Missing" for the alert, since FR-013 recomputes Status independently of the "MISSING" label the record was originally stored under — the two are different signals (why it was captured vs. its current state at send time).
- What happens if two alert runs are triggered within the same second? Their Excel attachments could share the same file name under the second-level timestamp pattern; this is treated as an acceptable, low-probability collision for a diagnostic/manual-trigger feature (see Assumptions) rather than a case this feature guards against.
- What happens if building the Excel attachment fails for some reason while the email and in-app notification would otherwise succeed? Out of scope for this feature to define custom recovery; the existing alert-sending error handling (FR-011's outer try/catch, per research.md R6) applies uniformly to the whole notification step, including attachment generation.
- What happens when multiple open sales orders share the same Master code, Code, Type, and Product and each was individually stored as MISSING (per FR-007)? The alert-building read still deduplicates by that four-column combination, so these records collapse into one row instead of appearing once per sales order; unlike before the 2026-08-20 combined-column update, the Sales order affiliation of each underlying stored record is not lost — it is preserved and shown, combined, in that row's Sales order column (Acceptance Scenario 17).
- What happens if two records sharing the same Master code, Code, Type, and Product combination somehow differ in another column (e.g. Description or Responsible emails) because of stale or inconsistent data? This is not expected to occur, since those four fields fully identify the same compliance master/reference-type mapping and the remaining columns are derived from that same master lookup; this feature does not define tie-breaking behavior for that case (see Assumptions).
- What happens if a record's Status changes between when the email body is rendered and when the Excel attachment is built? Both are generated from the same current set of records (FR-008) within the same alert-send operation, and Status is computed the same way (FR-013) for both, so the two representations always agree on which rows are Expired; this feature does not define behavior for the two diverging, since nothing in the process re-reads or re-evaluates the records between building the email and building the attachment.
- What order do the combined sales order codes appear in within the Sales order column when a group has more than one? Not specified by the user's request beyond the example ("SO1, SO2"); this feature does not require a specific sort order (e.g. alphabetical), only that the combined value lists every distinct contributing sales order code exactly once, comma-and-space separated (see Assumptions).
- What happens when an open sales order's delivery date is a genuine date but still lies far outside a compliance master's validity window as of today (e.g., a real past or future delivery date, not the placeholder)? This feature does not change that outcome — the check date fallback (FR-020) applies only when the delivery date is absent or is the "no date recorded" placeholder; a real delivery date is used as-is, and the resulting Missing/Valid/Expired determination for that date is expected to differ from "as of today" by design, consistent with prior behavior.
- What happens if the source system's "no date recorded" placeholder convention changes or a different placeholder value is introduced for a different data source in the future? Out of scope for this feature; it only defines the fallback for the specific placeholder value already used by the existing open-sales-order reference data source (see Assumptions).
- What happens if the email body's header styling itself changes in the future (a different background color, for instance)? Out of scope for this feature to define; the requirement is that the Excel header stays visually consistent with whatever the email header currently uses, not a specific fixed color captured independently in this spec.
- What happens to the underlying `compl_so_missing` store and the existing test-sales-order-alert trigger when the diagnostic without-Sales-order trigger is invoked? Both are unaffected — the diagnostic trigger reuses the same refresh and read-back logic; only the column projection used to build its own alert content differs (FR-024).
- What happens if the existing test-sales-order-alert trigger and the new diagnostic trigger are invoked around the same time? Out of scope for concurrency guarding, consistent with the existing repeated-trigger Edge Case; each independently clears and repopulates the same shared store, so whichever run finishes last determines what is actually stored, but each trigger still sends its own alert reflecting whatever it read back after its own refresh step.
- What happens if, after excluding its group per FR-026 or FR-027, a trigger has no remaining recipient emails at all (e.g., the current records' Responsible/Alert groups resolve to only the excluded group, with no other emails)? The existing no-recipient handling already in place applies unchanged: no email is sent and no in-app notification is produced for that run.
- What happens to the Responsible emails column shown in the alert content (FR-012) when the test-sales-order-alert-without-salesId trigger excludes the Responsible emails group from its recipients? The column still displays each record's responsible emails as data, unchanged — FR-026/FR-027 only affect who the alert is addressed to, not what the alert's content shows.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a manually-triggerable entry point (mirroring the existing manual compliance-alert test trigger) that runs the full sales-order missing-compliance refresh-and-notify process on demand.
- **FR-002**: System MUST retrieve the current list of open sales orders from the existing open-sales-order reference data source, with at minimum each sales order's code, delivery date, and customer account.
- **FR-003**: System MUST evaluate every open sales order retrieved in FR-002, one at a time, until the entire list has been processed.
- **FR-004**: For each open sales order, System MUST look up its compliance status through the existing per-reference compliance lookup, keyed by that sales order's code, delivery date, and customer account.
- **FR-005**: From each sales order's compliance lookup result, System MUST identify only the entries whose status is MISSING.
- **FR-006**: Before evaluating any open sales order, System MUST delete every existing record in the missing-compliance store, so no entries from a previous run persist into the current one.
- **FR-007**: System MUST store each identified MISSING entry against its owning sales order's code, carrying over all other compliance detail fields returned by the lookup for that entry.
- **FR-008**: After every open sales order has been processed, System MUST read back the current set of missing-compliance records as the basis for the alert, deduplicated by the combination of Master code, Code, Type, and Product, so that each distinct combination contributes exactly one record to the alert regardless of how many sales orders in the store share it. For each resulting alert record, System MUST retain the set of distinct sales order codes from every underlying stored record that was collapsed into it, for use by FR-019.
- **FR-009**: System MUST send exactly one consolidated alert (email plus in-app notification) summarizing the complete set of current missing-compliance records read in FR-008, using the same alert delivery mechanism (recipient resolution, formatting, notification persistence) as other existing compliance alerts.
- **FR-010**: System MUST NOT send an alert when the current set of missing-compliance records is empty (no open sales order that failed the lookup, or none reporting MISSING items, after processing).
- **FR-011**: A failure evaluating one open sales order's compliance lookup MUST NOT stop the system from evaluating the remaining open sales orders in the same run.
- **FR-012**: The alert generated in FR-009 MUST present, for every current missing-compliance record, exactly the following columns in this order: Master code, Master name, Status, Code, Name, Valid from, Valid to, Days remaining, Responsible emails, Description, Type, Product, Product name, Sales order. Sales order MUST be the last column.
- **FR-013**: System MUST compute each record's Status column at the moment the alert is generated (not reuse any previously stored status value), using that record's Code and Valid To values: "Missing" when Code is empty; "Expired" when Code is present and Valid To is earlier than the current date; "Valid" when Code is present and Valid To is either absent or not earlier than the current date.
- **FR-014**: System MUST compute each record's Days remaining column at the moment the alert is generated: left blank when Valid To is absent; otherwise shown as the number of days between the current date and Valid To, formatted as "N days left" where N is positive when Valid To is in the future (time remaining before expiry) and negative, shown with a leading minus sign (e.g. "-5 days left"), when Valid To has already passed (time since expiry).
- **FR-015**: Whenever the alert email is sent (FR-009), System MUST attach to that email an Excel file containing the same columns, in the same order, and the same computed values (including Status and Days remaining) as the email body (FR-012–FR-014).
- **FR-016**: The Excel attachment's file name MUST follow the pattern `compl-sales-order-missing-<yyyyMMddHHmmss>`, where the timestamp is the moment the alert was generated.
- **FR-017**: System MUST NOT produce an Excel attachment when no alert email is sent (FR-010).
- **FR-018**: Within the Excel attachment (FR-015), System MUST highlight each row whose Status (FR-013) is "Expired" with the same yellow background color already used to highlight that record's row in the email body, and MUST NOT apply that highlight to rows whose Status is "Missing" or "Valid".
- **FR-019**: For every alert record's Sales order column (FR-012), System MUST show every distinct sales order code retained for that record in FR-008, combined into a single value with each code separated by ", " (e.g. "SO1, SO2"), listing each contributing sales order code exactly once regardless of how many underlying stored rows it appeared in.
- **FR-020**: Before using an open sales order's delivery date as the check date for its compliance lookup (FR-004), System MUST substitute today's date whenever that delivery date is absent or equals the source system's "no date recorded" placeholder value; otherwise System MUST use the delivery date as-is, unchanged from prior behavior.
- **FR-021**: The check date determination in FR-020 MUST produce the same result that the compliance screen already uses when a stakeholder opens the same sales order without specifying an explicit date filter, so this feature's missing-compliance evaluation for a given sales order agrees with what the compliance screen currently shows for that sales order on the same day.
- **FR-022**: Within the Excel attachment (FR-015), System MUST style the header row (column titles) with the same background color, bold text, and cell borders already used for the header row in the email body, so the two representations of the alert present a visually matching header.
- **FR-023**: System MUST provide a second manually-triggerable entry point, distinct from FR-001, that runs the identical refresh-and-notify process as FR-001, differing only in the alert content produced for that trigger's own send (FR-024).
- **FR-024**: For the entry point in FR-023, System MUST omit the Sales order column entirely from both the email body and the Excel attachment of the alert it sends — not present as a header and not shown as an empty/blank column — while presenting all other columns, values, computed Status/Days remaining, Expired-row highlighting, and header styling identically to FR-012 through FR-018 and FR-022.
- **FR-025**: For the entry point in FR-023, since its alert content is no longer specific to individual sales orders (FR-024), System MUST use "Missing compliance Information" as that alert's title (the email subject and the heading shown above the table in the email body), instead of the existing trigger's "Sales orders with missing compliance" title.
- **FR-026**: For the entry point in FR-001 (test-sales-order-alert), System MUST NOT include any email address belonging to the Alert emails recipient group in that send's email (To or Cc) or in-app notification recipients — that trigger's alert continues to reach the Responsible emails recipient group as before.
- **FR-027**: For the entry point in FR-023 (test-sales-order-alert-without-salesId), System MUST NOT include any email address belonging to the Responsible emails recipient group in that send's email (To or Cc) or in-app notification recipients — that trigger's alert continues to reach the Alert emails recipient group as before.
- **FR-028**: The recipient-group exclusions in FR-026 and FR-027 MUST NOT alter either trigger's alert content — columns shown (FR-012/FR-024), the Responsible emails column's displayed value, computed Status/Days remaining (FR-013/FR-014), Expired-row highlighting (FR-018), header styling (FR-022), or title (FR-025) are unchanged; only which addresses receive the alert differs.

### Key Entities

- **Open Sales Order**: A sales order currently in "open" status, sourced from existing reference data. Key attributes used by this feature: code, delivery date, customer account. The delivery date may be absent or set to the source system's "no date recorded" placeholder value for a sales order that has not yet been scheduled; per FR-020/FR-021, this feature treats that placeholder the same way the compliance screen does — substituting today's date for the compliance lookup rather than passing the placeholder through unchanged.
- **Missing Compliance Record**: One entry representing a compliance item found to be MISSING for a specific open sales order at the time of the last refresh. Key attributes: the owning sales order's code, plus the full compliance detail (compliance master identifiers/names, validity window, description, responsible/alert recipient groups, and related reference-type mapping) as returned by the per-reference compliance lookup. Every refresh clears the entire store before repopulating it, so the stored records always reflect only the current run's evaluation, never a mix of runs. The stored record still keeps the owning sales order's code (unchanged by this update); the read used to build the alert deduplicates by Master code, Code, Type, and Product, and retains the distinct set of sales order codes collapsed into each resulting alert record (FR-008), for display in that record's Sales order column.
- **Compliance Alert Notification**: The single consolidated email and in-app notification sent after a refresh, summarizing all current Missing Compliance Records read back deduplicated by Master code, Code, Type, and Product, consistent in shape and recipients with other existing compliance alerts in the system. Presents a fixed set of 14 columns per record (Master code, Master name, Status, Code, Name, Valid from, Valid to, Days remaining, Responsible emails, Description, Type, Product, Product name, Sales order — Sales order last), where Status and Days remaining are recalculated at generation time from each record's Code and Valid To rather than carried over unchanged from storage, and Sales order shows every distinct sales order code collapsed into that record, combined into one value (e.g. "SO1, SO2"). Rows whose Status is "Expired" are highlighted with a yellow background in both the email body and the Excel attachment; other rows are not highlighted. When sent, it also carries one Excel file attachment mirroring the same columns, data, and Expired-row highlighting, named `compl-sales-order-missing-<yyyyMMddHHmmss>` after the alert's generation timestamp, whose header row is styled (background color, bold text, cell borders) to visually match the email body's header row. A diagnostic variant of this notification, triggered separately (FR-023), presents the same current record set and the same computed values but omits the Sales order column entirely — 13 columns instead of 14 — from both the email body and the Excel attachment (FR-024), and uses "Missing compliance Information" as its title instead of "Sales orders with missing compliance" (FR-025). As of the 2026-09-03 update, the two triggers also diverge in who they notify: the test-sales-order-alert trigger's notification excludes the Alert emails group (FR-026), while the test-sales-order-alert-without-salesId trigger's notification excludes the Responsible emails group (FR-027); neither exclusion changes the notification's content (FR-028).
- **Recipient Group**: One of the two named sets of email addresses this feature resolves per current record — Responsible emails (from each record's responsible/`RespGroups` recipients) and Alert emails (from each record's alert/`AlertGroups` recipients) — and combines across all current records into that trigger's overall recipient list. Prior to the 2026-09-03 update, both triggers addressed the alert to the union of both groups (Responsible emails as To, Alert emails as Cc). As of that update, each trigger excludes one specific group from its own send (FR-026, FR-027) while continuing to include the other; this exclusion applies identically to that trigger's email addressing and its in-app notification recipients, since both are built from the same resolved recipient list.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every open sales order returned at the start of a run is evaluated exactly once by the end of that run — 0 sales orders skipped, absent a lookup failure (see FR-011).
- **SC-002**: After a run completes, the missing-compliance store contains only records produced during that run — none carried over from any earlier run — and reflects exactly the compliance items actually missing for every successfully-evaluated sales order.
- **SC-003**: Responsible stakeholders receive exactly one alert per triggered run that has at least one current missing-compliance record — never zero when records exist, and never more than one.
- **SC-004**: An administrator or tester can trigger a full refresh-and-notify run on demand and observe the missing-compliance store fully refreshed without any manual follow-up step.
- **SC-005**: For every record shown in a sent alert, its Status and Days remaining values are consistent with that record's Code and Valid To values as of the moment the alert was generated — 0 records showing a stale or mismatched Status or Days remaining value.
- **SC-006**: Every alert email that is sent includes exactly one Excel attachment whose columns and data match the email body record-for-record, and whose file name follows the `compl-sales-order-missing-<yyyyMMddHHmmss>` pattern — 0 sent alerts missing the attachment or carrying mismatched data.
- **SC-007**: In every sent alert (email and Excel attachment), each distinct Master code/Code/Type/Product combination appears exactly once, and a Sales order column is present as the last column — 0 duplicate rows for the same combination.
- **SC-008**: In every sent alert's Excel attachment, the set of rows highlighted yellow exactly matches the set of rows shown as Expired in the email body — 0 Expired rows left unhighlighted in the attachment and 0 non-Expired rows incorrectly highlighted.
- **SC-009**: For every row in a sent alert, its Sales order column contains every distinct sales order code that contributed to that row's Master code/Code/Type/Product combination, each appearing exactly once — 0 rows missing a contributing sales order code and 0 rows with a duplicated or omitted code in that column.
- **SC-010**: For every open sales order whose delivery date is absent or equals the "no date recorded" placeholder, its missing-compliance determination during a run matches what the compliance screen shows for that same sales order on the same day — 0 sales orders reported as missing by this feature that the compliance screen shows as currently valid (or vice versa) solely due to the placeholder date being used instead of today.
- **SC-011**: In every sent alert's Excel attachment, the header row's background color, text weight, and cell borders visually match the header row in the email body — 0 sent alerts with an unstyled or mismatched Excel header row.
- **SC-012**: Every alert sent by the diagnostic without-Sales-order trigger contains exactly 13 columns (no Sales order column, in header or data) in both the email body and the Excel attachment, with every other column's values matching what the existing test-sales-order-alert trigger would produce from the same underlying data — 0 sent diagnostic alerts showing a Sales order column, blank or otherwise.
- **SC-013**: Every alert sent by the diagnostic without-Sales-order trigger shows "Missing compliance Information" as its title (email subject and body heading) — 0 sent diagnostic alerts titled "Sales orders with missing compliance"; the existing test-sales-order-alert trigger's alerts continue to show "Sales orders with missing compliance" unchanged.
- **SC-014**: Across every alert sent by the test-sales-order-alert trigger, 0 email addresses from the Alert emails recipient group appear in the email's To/Cc line or in the in-app notification recipients, while Responsible emails group addresses continue to receive that trigger's alert whenever the current record set resolves at least one.
- **SC-015**: Across every alert sent by the test-sales-order-alert-without-salesId trigger, 0 email addresses from the Responsible emails recipient group appear in the email's To/Cc line or in the in-app notification recipients, while Alert emails group addresses continue to receive that trigger's alert whenever the current record set resolves at least one.

## Assumptions

- This feature reuses three existing capabilities as-is and does not change their behavior: the open-sales-order reference data lookup, the per-reference compliance lookup (the one that reports item status including MISSING), and the existing compliance alert delivery mechanism (email plus in-app notification, including recipient resolution).
- The manual trigger described in User Story 2, Acceptance Scenario 3 is a diagnostic/testing entry point only, mirroring the existing manual compliance-alert test trigger; scheduling or automating recurring runs is out of scope for this feature.
- The missing-compliance store is a single, durable table that is fully cleared once at the start of every run, before any sales order is evaluated, and then repopulated with that run's results; it holds only the latest run's results, not history across runs, and is never cleared or filtered on a per-sales-order-code basis.
- "Open" sales orders are determined entirely by the existing open-sales-order reference data source; this feature does not add its own open/closed logic.
- Recipients for the consolidated alert are resolved the same way as other existing compliance alerts (per-record responsible/alert groups), with no sales-order-specific recipient list.
- Because the store is cleared entirely before evaluation begins, no previously stored record can survive into a new run on its own; a sales order that is no longer open, or whose lookup fails during the run, simply has no records afterward unless it is itself evaluated and found to have MISSING items in that same run.
- "Valid" is the reasonable default Status label for a record whose Code is present and whose Valid To is either absent or not yet passed; the user's request only specified the "Missing" and "Expired" cases explicitly.
- Days remaining is expressed relative to the current date at the moment the alert is generated, not the date the record was originally stored — a positive count means the item is still within its valid window, a negative count (shown with a leading minus sign) means it has already expired.
- The Responsible emails column reflects the same recipient-group resolution the system already uses for other compliance alerts; this feature does not introduce a new way of deriving responsible emails.
- The Excel attachment's file name pattern (`compl-sales-order-missing-<yyyyMMddHHmmss>`) is understood to need a standard spreadsheet file extension (e.g. `.xlsx`) appended, since the user's requested pattern specifies only the base name and timestamp format.
- The Excel attachment is a new, always-produced summary of the whole run, distinct from any existing per-record file attachment behavior (e.g. attaching a record's own uploaded compliance document) elsewhere in the alert system; this feature does not change or gate that separate, existing behavior.
- Because the file name's timestamp has one-second resolution, two alert runs triggered within the same second could produce identically-named attachments; this is accepted as a low-probability edge case for a manually/diagnostically triggered feature rather than something requiring a uniqueness guarantee.
- "Visually match" for the Excel attachment's header row means the same background color, bold text weight, and cell borders as the email body's header row — not necessarily byte-identical formatting metadata, consistent with how the Expired-row yellow highlight (FR-018) was already interpreted as color equivalence rather than exact format duplication.
- Deduplicating by Master code, Code, Type, and Product is safe because those four fields together identify the same compliance master/reference-type mapping regardless of which sales order surfaced it; the remaining columns (Master name, Name, Valid from/to, Description, Responsible emails) are expected to be identical across records sharing that combination, so collapsing them loses no distinct information relevant to the alert.
- The 2026-08-18 update's removal of the Sales order column from the alert is superseded by the 2026-08-20 combined-column update below; it no longer applies to the alert's displayed columns. It remains true, unchanged, that the `compl_so_missing` store continues to record and key on the owning sales order's code exactly as before (FR-006, FR-007), and no other feature or screen that reads that store directly is affected by either update.
- "The same yellow" means the Excel attachment's Expired-row highlight is visually equivalent to the email body's existing Expired-row highlight (same color); this feature does not introduce a different color for the attachment, and does not change which rows are considered Expired (FR-013 already governs that).
- Highlighting is applied per row across all of that row's columns in the Excel attachment (i.e., the whole row reads as highlighted), matching how the email body highlights a full table row rather than an individual cell.
- "Combine thành 1 dòng" (combined into one cell/value) is interpreted as a comma-and-space-separated list of the distinct contributing sales order codes (e.g. "SO1, SO2"), matching the user's own example, rather than a separate row per code or a different delimiter (e.g. line breaks); this is a plain single-line list, unlike the `<br/>`-joined multi-line format already used for the Responsible emails column.
- The Sales order column reintroduced by the 2026-08-20 update is a display-only, read-back-time value (built from the distinct sales order codes retained per FR-008) — it is not a new stored column on `compl_so_missing` or `ComplSoMissingResponseDto`, consistent with how Status and Days remaining (FR-013/FR-014) are also computed at alert-generation time rather than persisted.
- The compliance screen's own fallback-to-today behavior (when a sales order's delivery date is absent or is the source system's "no date recorded" placeholder) is treated as the reference behavior this feature's evaluation must match; this feature does not change the screen's behavior, only aligns this feature's own check-date determination (FR-020/FR-021) to agree with it for the same sales order on the same day.
- "Today" for the FR-020 fallback means the date at the moment each sales order is evaluated during a run, consistent with how the compliance screen determines "today" when a user opens it without an explicit date filter; this feature does not freeze a single "today" value for the whole run if a run happens to span a date rollover, since that is already how the reference screen behavior works.
- FR-020's fallback only substitutes today's date for an absent or placeholder delivery date; it does not change how a genuine, non-placeholder delivery date is used, so sales orders with a real delivery date continue to be evaluated exactly as before this update.
- The diagnostic entry point (FR-023) is a manual/testing-only trigger, mirroring the relationship the existing test-sales-order-alert trigger already has to the feature's scheduled/production job; this feature does not add a corresponding scheduled/automated job for the diagnostic variant.
- "Không có cột SalesId" (no SalesId column) is interpreted as removing the Sales order column entirely from both the email table and the Excel sheet for the diagnostic trigger's own send — not leaving the column present but blank — consistent with how every other column in this alert always pairs a header with data.
- Because the diagnostic trigger (FR-023) reads back and sends from the same shared `compl_so_missing` store as the existing trigger, it does not require its own store, its own refresh logic, or a separate deduplication rule; it only needs a different column projection when building its own alert's email body and Excel attachment.
- "Missing compliance Information" (FR-025) is used verbatim, with that exact capitalization, as given in the user's request; it replaces the title only for the diagnostic trigger's own alert and does not introduce a general mechanism for customizing the title of other alerts in the system.
- "Không gửi email cho nhóm X" (will not send email to group X, FR-026/FR-027) is interpreted as excluding that group from the trigger's entire resolved recipient list, which is shared between the email's To/Cc addressing and the in-app notification recipients in the existing implementation — not as a channel-specific exclusion that would still notify the group in-app while omitting only the email. This keeps the exclusion consistent across both channels of the same alert rather than introducing a new, more granular per-channel recipient rule.
- The Alert emails group and Responsible emails group are the two recipient groups already resolved per current record (from each record's alert/responsible group recipients) prior to this update; this update does not change how either group's member emails are resolved, only whether a given trigger's own send includes that group.
- Excluding a recipient group from one trigger's send (FR-026/FR-027) does not exclude that group from the other trigger's send, nor from any other existing alert in the system (e.g. the general test-alert or manual-alert triggers); the exclusion is scoped to that one trigger's own alert only.
